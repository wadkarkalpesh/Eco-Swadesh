Purpose Sequences the 191 story points across 44 stories (Document 5, §14 roll-up) into an executable phase plan, from discovery through production launch, with explicit objectives, deliverables, milestones, risks, dependencies, timeline bands, and a Definition of Done (DoD) per phase. 2. Scope Covers Phase 0 (this documentation effort) through Phase 10 (production launch) for the India market. Post-launch international expansion phases are referenced but detailed separately once Phase 10 is complete (Document 2 §13.1). 3. Goals No phase begins without its dependencies from prior phases satisfied — sequencing is a first-class constraint, not an afterthought. Every phase ends with a testable Definition of Done, not a vague “ mostly working ” state. Timeline bands are relative-effort estimates derived from Document 5’s story points, not committed calendar dates (team velocity is unknown pre-Phase 1). 4. Phase 0 — Discovery, Planning, Research Objectives: Establish problem validity, vision, requirements, and technical direction before writing product code. Deliverables: Documents 1–9 (this documentation set), plus the /diagrams source folder. Milestones: All Phase 0 documents reviewed and signed off by founders/product lead. Risks: Assumptions flagged throughout Documents 1–9 (diaspora willingness-to-pay, expert participation, producer trust, Razorpay onboarding specifics) remain unvalidated with primary research; Phase 1 planning should not silently convert these into hard requirements. Dependencies: None — this is the root phase. Timeline band: Complete (this document is the closing deliverable of Phase 0). Definition of Done: All 10 documents exist, are internally consistent (cross-references resolve), and assumptions are explicitly catalogued rather than buried in prose. 6. Phase 1 — Foundation Objectives: Stand up the technical skeleton so every later phase has somewhere to build. Deliverables: - Firebase projects provisioned (dev/staging/prod, per Document 8 §6) - Expo project scaffolded on current stable SDK (Document 9 §4) - CI pipeline live (GitHub Actions lint/type-check/test, per Document 8 §14) - Firestore base schema deployed (Document 7 §5) with security rules skeleton (Document 7 §7) - Role-aware navigation shell (Document 6 §4) with placeholder screens Milestones: A blank-but-navigable app builds successfully via EAS and installs on a test device for both iOS and Android. Risks: Underestimating Expo/Firebase project configuration time (multi-environment setup is easy to shortcut and hard to retrofit). Dependencies: Phase 0 sign-off; Firebase/GCP account and billing setup (business dependency, not engineering). Timeline band: Small — primarily infrastructure setup, low story-point weight but high blocking risk if rushed. Definition of Done: CI green on a trivial PR; app installable on both platforms; Firestore rules pass the emulator test suite described in Document 7 §7. 7. Phase 2 — Authentication Objectives: Implement the Authentication epic (Document 5, §2 — AUTH-1 through AUTH-5). Deliverables: Phone/OTP and email registration/login (UC-01), multi-role account model (AUTH-3), password/PIN reset (AUTH-4), Expert credential submission flow feeding into the moderation queue stub (AUTH-5). Milestones: A user can register, verify, select roles, and log back in reliably. Risks: SMS/OTP delivery reliability in the target launch region — flagged as a vendor-selection task, not assumed solved by default Firebase Auth SMS. Dependencies: Phase 1 Firestore schema and navigation shell. Timeline band: Medium (20 points per Document 5 §14 roll-up). Definition of Done: All AUTH-1–5 acceptance criteria (Document 5 §2) pass QA; custom claims correctly populate roles on the auth token (Document 8 §11). 8. Phase 3 — Marketplace Objectives: Implement core browse/search/listing creation (Document 5 §3 — MKT-1 through MKT-5), without yet wiring certification or checkout. Deliverables: Listing creation with draft support (MKT-1, MKT-2), search/filter (MKT-3 — filters functional even if certification filter shows only “ unverified ” until Phase 4), listing edit/deactivate (MKT-5). Milestones: A Seller can publish a listing; a Buyer/Guest can find it via search. Risks: Building search/filter UI before the certification data model (Phase 4) exists risks rework if the filter taxonomy changes — mitigate by finalizing the certSchemes reference collection (Document 7 §5) conceptually in this phase even though verification logic ships in Phase 4. Dependencies: Phase 2 authentication and roles. Timeline band: Medium (18 points). Definition of Done: MKT-1–5 acceptance criteria pass QA; offline draft-save verified on a throttled/offline test connection (SRS §2.4). 9. Phase 4 — Seller &amp; Trust (Certification) Objectives: Implement the Trust &amp; Certification epic in full (Document 5 §4 — TRUST-1 through TRUST-5) — the platform’s core differentiator (Document 2 §11–13). Deliverables: Certification submission (TRUST-1), moderator verification workflow (TRUST-2), Trust Score computation (TRUST-3), post-delivery reviews tied to completed orders (TRUST-4 — stubbed pending Phase 5 orders), certification expiry alerts (TRUST-5). Milestones: A Seller can submit NPOP/PGS-India certification; a Moderator can approve it; the listing’s Trust Score and label update automatically, satisfying MKT-4’s acceptance criteria from Phase 3. Risks: This phase carries the highest single-epic story-point weight (27 points, Document 5 §14) and the highest business risk if trust integrity is compromised — extra QA rigor is warranted here specifically, not uniformly across all phases. Dependencies: Phase 3 listings; Phase 2 moderator role. Timeline band: Large (27 points — the single heaviest epic). Definition of Done: TRUST-1–5 acceptance criteria pass QA; every verification decision is confirmed logged to auditLog (Document 7 §5) with moderator identity and timestamp, satisfying SRS FR-11. 10. Phase 5 — Orders &amp; Payments Objectives: Implement Orders and Payments epics (Document 5 §5–6 — ORD-1 through ORD-5, PAY-1 through PAY-3), including the revised dual-gateway architecture (Document 9 §7). Deliverables: Cart/checkout (ORD-1, PAY-1 via Razorpay), order tracking (ORD-2), delivery status updates (ORD-3), cancellation (ORD-4), seller order history (ORD-5), saved payment methods (PAY-2), payout ledger (PAY-3 via Razorpay Route). Milestones: A Buyer completes an end-to-end purchase; a Seller sees a payout reflected in their ledger. Risks: Multi-gateway payout reconciliation (Document 9 §7 risk) is genuinely complex — budget explicit QA time for reconciliation edge cases (partial refunds, multi-seller cart splitting) rather than treating payments as “ just an API integration. ” Dependencies: Phase 4 Trust Score (for order-item certification snapshotting, Document 7 §5); Phase 3 listings. Timeline band: Large (35 points combined — Orders 19 + Payments 16). Definition of Done: ORD/PAY acceptance criteria pass QA; a test transaction settles correctly through Razorpay Route with the platform commission correctly split, verified against the actual Razorpay sandbox, not mocked. 11. Phase 6 — Community Objectives: Implement Messaging/Community epic (Document 5 §8 — COMM-1 through COMM-4). Deliverables: Question posting (COMM-1), Expert-badge answer distinction (COMM-2), order-scoped buyer/seller messaging (COMM-3), moderation of flagged posts (COMM-4). Milestones: A Buyer/Seller can post a question and receive a visibly-badged Expert answer. Risks: Community features risk an “ empty room ” launch problem (Document 2 §7.5) if not seeded with initial content/experts before public launch — this is a go-to-market dependency, not purely an engineering one. Dependencies: Phase 2 Expert credentialing (AUTH-5); Phase 5 orders (for order-scoped messaging, COMM-3). Timeline band: Medium (16 points). Definition of Done: COMM-1–4 acceptance criteria pass QA; at least a handful of seeded expert answers exist in staging before production content seeding begins. 12. Phase 7 — AI Assistant Objectives: Implement AI Assistant epic (Document 5 §9 — AI-1 through AI-3). Deliverables: Photo-based diagnosis (AI-1), low-confidence escalation to human expert (AI-2), general conversational assistant (AI-3). Milestones: A photo upload returns a diagnosis within the SRS-specified 5–10 second window (§3.2.1), with a working escalation path into Phase 6’s community/expert flow. Risks: AI Service vendor selection and cost-per-call have not been finalized in Documents 1–9 — flagged as an open dependency to resolve before this phase’s sprint planning, not assumed free. Dependencies: Phase 6 community (for escalation target); Phase 1 camera/media handling. Timeline band: Medium (18 points). Definition of Done: AI-1–3 acceptance criteria pass QA; low-confidence responses are verified to proactively suggest escalation rather than silently presenting uncertain output as authoritative (Document 2 §7.3 principle). 13. Phase 8 — Admin Objectives: Implement Admin epic (Document 5 §12 — ADMIN-1 through ADMIN-3), unifying moderation across certification, listings, reviews, and community. Deliverables: Region/language/fee configuration (ADMIN-1), unified moderation queue (ADMIN-2), audit log viewer (ADMIN-3). Milestones: An Administrator can configure a new region’s fee structure without a code deploy, directly testing the founding brief’s “ no redesign for expansion ” mandate. Risks: This phase is the heaviest single Admin-side epic (21 points) and is easy to under-scope if treated as “ just an internal tool ” — the moderation queue is operationally load-bearing for the entire trust thesis (Document 2 §6). Dependencies: Phase 4 certification data model (moderation targets); can begin in parallel with Phases 5–7 once Phase 4 is complete (see §4 roadmap diagram note). Timeline band: Large (21 points). Definition of Done: ADMIN-1–3 acceptance criteria pass QA; a config-only region addition is demonstrated in staging without a code deployment. 14. Phase 9 — Testing Objectives: Full-system QA pass across all epics, accessibility and security verification, and analytics validation. Deliverables: - WCAG 2.2 AA conformance verification (automated scan + manual review, per SRS §4.1 — manual review is required because automated tooling alone catches only a fraction of accessibility failures ) - OWASP Mobile/Top 10 security review (Document 3 §3.2.5) - DPDP-compliant consent flow verification ahead of the Phase III deadline (Document 3 §3.2.6) - Analytics epic implementation and validation (Document 5 §13 — ANLY-1 through ANLY-3), confirming VTT (Document 2 §9.1) is actually computable end-to-end - Load testing against projected v1.0 transaction volume (Document 7 §10 assumption) Milestones: Zero “ Must ” -priority open defects (Document 3 §4.1 acceptance criteria); VTT dashboard shows real (staging) data correctly. Risks: Testing phases are the most commonly compressed under schedule pressure — this phase’s DoD should be treated as a hard gate, not a soft target, given how much of the differentiation thesis (trust integrity) depends on it actually working correctly. Dependencies: All of Phases 2–8 complete. Timeline band: Large — proportional to the cumulative 191 story points already built, not a fixed small buffer. Definition of Done: All acceptance criteria from Document 3 §4.1 met; independent (non-author) QA sign-off on WCAG and security review; DPDP consent flows reviewed against legal counsel, not just engineering self-assessment. 15. Phase 10 — Production Launch Objectives: Ship v1.0 to production for the India launch market. Deliverables: Production Firebase project cutover, EAS Submit to App Store/Play Store (Document 8 §6), production monitoring/alerting live (Document 8 §14), initial content/expert seeding (Phase 6 risk mitigation) complete before public announcement. Milestones: App live in both app stores; first real Verified Trusted Transaction recorded (Document 2 §9.1). Risks: App store review timelines (especially first submission) are outside the team’s direct control — buffer this phase’s timeline band accordingly rather than treating store approval as instantaneous. Dependencies: Phase 9 sign-off. Timeline band: Small (launch execution), but gated entirely by Phase 9’s hard quality bar. Definition of Done: App approved and live in both stores; production monitoring dashboards show green; VTT metric is live and reporting real transactions, not staging data. 16.
