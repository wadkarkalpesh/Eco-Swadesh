Security Rules — Representative Pattern service cloud.firestore { match /databases/{database}/documents { function isSignedIn() { return request.auth != null; } function hasRole(role) { return isSignedIn() &amp;&amp; role in request.auth.token.roles; } function isOwner(field) { return isSignedIn() &amp;&amp; request.auth.uid == resource.data[field]; } match /listings/{listingId} { allow get, list: if true; // public browse, per SRS FR-5 (Guest-accessible) allow create: if hasRole(&#39;seller&#39;) &amp;&amp; request.resource.data.sellerId == request.auth.uid; allow update, delete: if isOwner(&#39;sellerId&#39;) || hasRole(&#39;admin&#39;); } match /certifications/{certId} { allow get: if true; // trust info must be publicly visible, per Document 2 §6 allow create: if hasRole(&#39;seller&#39;); allow update: if hasRole(&#39;moderator&#39;) || hasRole(&#39;admin&#39;); // Sellers cannot self-approve their own certification — verification integrity (SRS FR-11) } match /orders/{orderId} { allow create: if hasRole(&#39;buyer&#39;) &amp;&amp; request.resource.data.buyerId == request.auth.uid; allow get: if isOwner(&#39;buyerId&#39;) || (isSignedIn() &amp;&amp; request.auth.uid in resource.data.sellerIds); allow update: if hasRole(&#39;admin&#39;); // status changes flow through Cloud Functions, not client } match /auditLog/{entryId} { allow read: if hasRole(&#39;admin&#39;) || hasRole(&#39;moderator&#39;); allow write: if false; // server-side (Cloud Functions) only } } } This follows the standard Firestore rules structure, where read rules can be divided into get (single-document reads) and list (queries/collection reads), and write rules into create , update , and delete , giving fine-grained control (e.g., public get on certifications for trust transparency, but no client write at all on the audit log). 7.1 Multi-region / future multi-tenant consideration Although Eco Swadesh is a single global platform rather than a multi-tenant SaaS, the same discipline applies across regions: encoding the region/ownership key directly in documents and Rules, rather than filtering after the fact, avoids both security leaks and expensive broad-scan queries as new regions are added . 8. Future Migration Path to PostgreSQL Firestore is deliberately chosen for v1.0 (rationale in Document 9) because of its native real-time listeners and zero-ops scaling for mobile-first read/write patterns. However, as SRS §3.2.2 requires, the schema above is designed so a future migration to PostgreSQL for relational reporting and analytics workloads (not necessarily full transactional replacement) is straightforward: Firestore construct PostgreSQL equivalent Migration note users/{userId} users table, user_roles join table roles array normalizes cleanly into a join table listings/{listingId} listings table Straightforward; certificationId becomes a foreign key certifications/{certId} certifications table + cert_schemes reference table scheme enum maps to a foreign key against cert_schemes orders + subcollection items orders + order_items tables Firestore subcollection maps 1:1 to a child table with order_id FK auditLog audit_log table, append-only, indexed by actor_id , target_id Direct copy; Firestore’s append-only pattern already matches relational audit-log conventions Recommended migration strategy (not yet executed, flagged for Document 10 roadmap): stream Firestore writes to BigQuery (via Cloud Functions triggers) for analytics from day one (Document 9 rationale), then evaluate a full or partial PostgreSQL migration once reporting complexity (multi-table joins, ad hoc analyst queries) outgrows what BigQuery-on-Firestore-export comfortably supports — this avoids a risky “ big bang ” migration and lets the team migrate read-heavy reporting workloads first while transactional writes remain on Firestore. 9. Decision Rationale Summary Firestore chosen for v1.0 for real-time listener support and reduced ops overhead (full comparative rationale in Document 9). Certification modeled as its own collection (not embedded in listings) so a producer’s certification can be referenced by multiple listings and audited independently — directly serving Document 2’s certification-as-first-class-object principle. Order items snapshot certification status at purchase time to preserve historical trust claims even if a certification later expires or is revoked — this is a deliberate design choice protecting both buyer and platform in disputes. 10. Assumptions [Assumption] Firestore’s document size and write-rate limits will comfortably support the projected v1.0–v2 transaction volume; to be load-tested before international rollout, not assumed indefinitely. [Assumption] BigQuery export via Cloud Functions triggers is sufficient for early analytics needs (Document 5, ANLY-1/2/3) without requiring the PostgreSQL migration in Year 1. 11. Risks Firestore’s lack of native multi-document ACID transactions across very large fan-outs could complicate certain future features (e.g., large multi-seller order splitting); Cloud Firestore transactions are scoped and should be tested against real order-splitting scenarios before Document 5’s PAY-3 (payout ledger) is finalized in engineering. Over-denormalization (e.g., trustLabel copied onto listings) creates a data-consistency obligation: certification expiry (Document 5, TRUST-5) must reliably trigger a Cloud Function update to every denormalized copy, or trust labels can go stale — this is a first-class engineering risk, not a minor detail. 12. Future Considerations Full-text search (e.g., searching listing descriptions) is out of scope for Firestore’s native query engine; per current guidance, full-text search should be handled by mirroring tenant-/region-scoped documents into a dedicated search service such as Algolia or Meilisearch, storing only IDs and minimal denormalized fields to rebuild views — flagged as a Document 10 roadmap item, not a v1.0 requirement. As certification-body APIs mature (Document 1, §13), the certifications collection’s documentRef field can evolve from a manually-uploaded document reference to a live API-verified reference without a schema change. 13. Network Architecture All client-to-backend traffic over TLS 1.2+; Firebase SDKs handle this by default. Cloud Functions act as the trust boundary for anything touching payments, certification approval, or audit logging — clients never call external payment/AI APIs directly (mirrors Document 7 §7 security rules pattern of “ server-side only ” writes for sensitive state). CDN in front of Cloud Storage for product images, reducing load-time on low-bandwidth rural connections (SRS §2.4, §3.2.1). 8. Frontend Architecture React Native + Expo , using the New Architecture (Fabric/JSI/TurboModules), which is now the industry default rather than an experimental option: React Native 0.82 was the first version to remove the option to disable the New Architecture, and Expo SDK 55 runs on React Native 0.83 , so Eco Swadesh should target a current SDK line rather than legacy-architecture builds from the outset (full rationale in Document 9). State management: local/UI state via a lightweight store (e.g., Zustand-pattern), server state via query-caching layer — avoids the “ Redux for everything ” pattern that current React Native guidance considers outdated for new projects. Role-aware navigation (Document 6) implemented via a single navigation tree with conditional route visibility, not separate app bundles per role. Offline-first drafts (Document 5, MKT-2) implemented via local persistence synced to Firestore when connectivity returns, using Firestore’s built-in offline persistence rather than a custom cache layer. 9. Backend Architecture Cloud Functions organized by domain (auth, trust, orders, notifications, moderation — per §5 component diagram), each independently deployable and stateless, satisfying SRS §3.2.2 scalability requirements. Certification verification and audit-log writes are Cloud-Functions-only paths (no direct client writes), enforced at both the Firestore Rules layer (Document 7 §7) and the Cloud Functions authorization layer (defense in depth). 10. Cloud Architecture GCP/Firebase as the primary cloud, chosen for tight Firestore/Auth/Functions/Storage integration and reduced early-stage ops burden (full comparative rationale in Document 9). Region selection: primary Firestore region set for lowest latency to the India launch market, with multi-region read replicas evaluated ahead of the second-market launch (Document 2 §13.1) rather than at v1.0. 11. Authentication Architecture Firebase Authentication as the identity provider (phone/OTP, email, and social login per SRS FR-1). Custom claims used to encode roles (buyer/seller/expert/gardener/moderator/admin) directly on the auth token, which Firestore Security Rules then read via request.auth.token.roles (Document 7 §7) — this keeps role checks fast and avoids extra document reads on every rule evaluation. 12. Notification Architecture Firebase Cloud Messaging (FCM) for push; Cloud Functions triggers on relevant Firestore writes (order status change, certification approaching expiry — Document 5 TRUS-5, NOTIF-1) fan out to FCM plus an in-app notification subcollection (Document 7 §5, notifications/{userId}/items/{notificationId} ) as a fallback channel, satisfying SRS’s “ at least one channel even if push fails ” requirement (§3.2 FR-9 note). 13. Storage Architecture Cloud Storage buckets separated by sensitivity: listings-media (public-readable images) vs. certification-docs (restricted, moderator/admin-only access via Storage Security Rules mirroring the Firestore pattern in Document 7 §7). Signed URLs used for certification document access to avoid permanent public exposure of sensitive producer documents. 14. Caching Strategy CDN caching for static product images (§7). Client-side query result caching (short TTL) for marketplace browse/search to reduce redundant Firestore reads, aligned with the read-cost-reduction guidance of designing queries per-screen and caching on the client to control Firestore read costs referenced in Document 7. 17. Scalability Strategy Stateless Cloud Functions scale horizontally by default under GCP’s managed infrastructure. Firestore composite indexes scoped tightly to actual screen queries (Document 7 §6) to keep write-cost and latency predictable as listing/order volume grows. Search scaling path (Algolia/Meilisearch mirroring, Document 7 §12) planned ahead of the point where marketplace browse volume would otherwise degrade Firestore query performance. 18. Future Microservices Consideration Cloud Functions’ domain-based organization (§5, §9) is deliberately structured so that any single domain (e.g., Trust Score computation, or AI orchestration) could be extracted into a dedicated service (e.g., Cloud Run) if its scaling or language requirements diverge from the rest of the backend — this is a future option, not a v1.0 requirement , consistent with the founding brief’s instruction to avoid premature complexity while not precluding it structurally. 19. Document 9 — Technology Decision Record Status: Draft v1.0 Builds on: Documents 1–8 Format: Each entry states the decision, alternatives considered, and why — following the same “ compare, then justify ” instruction from the founding brief. Correction note vs. the original founding brief: the brief listed “ Official Stripe documentation ” as a research input assuming Stripe as the payment gateway. Research for this document found that, as of the most recent verified data, Stripe is fully self-service supported in only 46 countries, with India currently in preview/invite-only access requiring direct sales contact rather than full self-service availability . Since India is Eco Swadesh’s launch market, this materially changes the payment gateway decision below — flagged explicitly rather than silently proceeding with the brief’s original assumption. 1. Purpose Documents why each core technology was chosen, not just what was chosen, so future engineers understand the trade-offs already considered instead of re-litigating them. 2. Scope Covers: React Native, Expo, JavaScript, React, Firebase, Firestore, Cloud Functions, Storage, Maps, Payments, Analytics, Push Notifications, CI/CD, Monitoring. 3. React Native Decision: React Native as the cross-platform mobile framework. Alternatives considered: Flutter, native iOS/Android (Swift/Kotlin) separately. Rationale: Single codebase for iOS/Android reduces team size needed at pre-seed/seed stage (Document 1 §5.1, small-team execution risk noted in SWOT). React Native’s ecosystem and hiring pool remain larger than Flutter’s for most markets, and the framework’s historical performance ceiling — the async bridge — has been structurally resolved: React Native’s New Architecture replaces the legacy async Bridge with JSI (JavaScript Interface), enabling synchronous JavaScript-to-native calls, and typical apps see 10–30% UI thread improvement, with up to 3x improvement in cross-thread call performance for native-module-heavy apps . Risk if not chosen: Native-only would double engineering headcount needs at a stage where Document 1’s SWOT already flags execution risk as a weakness. 4. Expo Decision: Expo (managed/prebuild workflow) on top of React Native. Alternatives considered: Bare React Native CLI. Rationale: The gap between managed Expo and bare React Native has nearly closed — Expo gives full native module access via development builds, New Architecture by default, and EAS tooling for builds and updates , and industry guidance for 2026 explicitly recommends Expo for most new projects, reserving bare React Native only for specific native integrations Expo’s plugin system cannot handle . As of the current SDK line, SDK 55 runs on React Native 0.83 and later SDKs run entirely on the New Architecture , and Expo SDK 56 (May 2026) supports React Native 0.85 — meaning Eco Swadesh should target the current stable SDK line rather than an older one, and plan SDK upgrades as a recurring roadmap item (Document 10), not a one-time decision. 5. JavaScript / React Decision: JavaScript (with TypeScript strongly recommended for the codebase, not optional) and React as the UI library underlying React Native. Rationale: Directly required by the React Native/Expo choice above; TypeScript is added as a project convention (not a separate “ technology decision ” ) to reduce runtime errors in a small team without a large dedicated QA function. 6. Firebase (Authentication, Firestore, Cloud Functions, Storage) Decision: Firebase as the backend platform for v1.0. Alternatives considered: Supabase (Postgres-based), custom Node.js/Express + PostgreSQL backend, AWS Amplify. Rationale: - Firestore gives native real-time listeners out of the box, which matters for order-status tracking (Document 5, ORD-2) and live moderation queues (Document 5, ADMIN-2) without building custom WebSocket infrastructure — Firestore provides native real-time listeners with automatic fan-out, letting the frontend subscribe directly to the database for live updates without routing every read through a backend , provided (as implemented in Document 7 §7) that security rules and scoped authentication tokens enforce isolation, not the client. - Cloud Functions provide the server-side trust boundary needed for certification verification and audit logging (Document 7 §7, Document 8 §9) without standing up and operating a separate server fleet — appropriate for the team-size constraint flagged in Document 1’s SWOT. - Zero-ops scaling matches the “ optimize for completeness and long-term success without over-engineering early ” spirit of the founding brief, while the Document 7 §8 migration plan to PostgreSQL for reporting keeps this from becoming a permanent constraint. Trade-off acknowledged: Firestore is not a relational database; multi-table joins and complex ad hoc analyst queries are weaker than PostgreSQL’s — this is precisely why Document 7 §8 defines an explicit BigQuery-export-now, PostgreSQL-migration-later path rather than presenting Firestore as a permanent, unqualified choice. 7. Payment Gateway — Revised Decision Original brief assumption: Stripe (globally). Research finding: Stripe carries heavy compliance baggage for India-based merchants specifically — because Stripe is an international entity, KYC and onboarding for Indian merchants can be arduous, and integrating deep India-localized payment flows (specific netbanking portals, regional wallets) feels like an afterthought compared to India-native gateways . Independently, Stripe relies on third-party aggregators to process UPI in India, adding latency and slightly reducing UPI success rates compared to India-native gateways, which maintain direct bank integrations and dynamically route around a struggling bank’s UPI switch . Revised decision: Razorpay as the primary payment gateway for the India launch , specifically using Razorpay Route for marketplace split-settlement (paying sellers their share net of Eco Swadesh’s commission automatically), with Stripe added for cross-border/diaspora buyer-facing collection once international expansion begins (Document 2 §13.1). Rationale: - For early-stage startups, Razorpay is the natural choice because it integrates in hours and handles everything; for marketplaces with vendor payouts specifically, Cashfree Payouts can be layered alongside Razorpay collections with two integrations, no overlap, no extra cost — validating a dual-gateway approach rather than forcing a single-vendor decision. - Both Razorpay and Cashfree hold operational Payment Aggregator licenses required under RBI regulation, and both boast UPI success rates north of 92% through intelligent dynamic bank routing , a reliability profile India-based Eco Swadesh sellers depend on directly for payout confidence (Document 5, PAY-3). - When Eco Swadesh expands to diaspora/international buyers (Document 2 §13.1), Stripe becomes appropriate specifically for that cross-border collection flow: Stripe’s global routing, foreign exchange handling, and billing infrastructure are unmatched for platforms whose primary customer base is international . Business rule implication (feeds Document 3 SRS and Document 7): the payment architecture must support multiple gateways per platform, selected by buyer region , from v1.0 — not a single hardcoded gateway — directly reinforcing the founding brief’s “ no redesign for expansion ” mandate. Risk: Running two payment integrations increases engineering and reconciliation complexity (Document 5, PAY-3 acceptance criteria must account for multi-gateway payout ledgers) — an explicit, accepted trade-off in exchange for launch-market payment reliability. 8. Maps / Geolocation Decision: Google Maps Platform for v1.0 , with an explicit architectural abstraction so Mapbox or OpenStreetMap/MapLibre can be substituted per-region without a client rewrite. Alternatives considered: Mapbox, OpenStreetMap + Leaflet/MapLibre, HERE, TomTom. Rationale: Google Maps offers comprehensive and accurate global map data with a familiar interface prioritizing seamless user experience and brand recognition , which matters for a trust-sensitive consumer product where an unfamiliar map UI could itself read as a minor trust signal risk. However, cost is a real and current concern: Google replaced its $200/month universal credit with per-SKU free usage caps in 2025/2026 — the free tier now covers roughly 28,500 map loads/month, with a Starter plan at $100/month for 50,000 calls and overage at $7 per 1,000 loads , whereas Mapbox offers nearly double the free web map loads (50,000/month) and cheaper overage ($5 per 1,000 loads, dropping further at scale) . Decision detail: Launch with Google Maps Platform for brand-familiarity reasons in the India launch market, but implement the maps integration behind an internal abstraction layer (a thin MapProvider interface in the frontend architecture, Document 8 §8) from day one, so that cost-sensitive regions or coverage gaps can switch to Mapbox/MapLibre+OSM without touching business logic — directly satisfying the founding brief’s “ no redesign for expansion ” mandate, and hedging against the specific coverage caveat that Mapbox/OSM-based coverage can be inconsistent in regions like India, Israel, or China for logistics-dependent use cases , which argues against jumping to OSM-only at launch. [Assumption] Actual usage-volume cost modeling (which specific Maps SKUs — geocoding, places autocomplete, static maps — Eco Swadesh will call, and how often per user session) has not yet been done; Document 8’s caching-strategy section (§16) should be revisited once real usage patterns are known, per the general guidance that architecture and call volume matter more to actual mapping cost than vendor choice alone . 9. Analytics Decision: Firebase Analytics (client-side event tracking) + BigQuery (via Firestore export, Document 7 §8) for the VTT North Star Metric and supporting metrics (Document 2 §9, Document 5 ANLY-1/2/3). Rationale: Native integration with the rest of the Firebase stack avoids a third analytics vendor at v1.0; BigQuery export gives the relational query power needed for cohort analysis (producer repeat-listing rate, cross-border transaction share) that Firestore’s native queries cannot do well. 10. Push Notifications Decision: Firebase Cloud Messaging (FCM). Rationale: Native integration with Firebase Auth/Firestore triggers (Document 8 §12); no separate push infrastructure vendor needed at v1.0 scale. 11. CI/CD Decision: GitHub Actions for CI (lint, type-check, tests) + EAS Build/Submit for mobile CD + Firebase CLI deploy for backend CD (full detail in Document 8 §14). Alternatives considered: Bitrise, CircleCI, Jenkins (self-hosted). Rationale: GitHub Actions requires no additional vendor account if the codebase is already on GitHub; EAS is Expo’s own managed build/submit service and is the path of least friction given the Expo decision above, avoiding the operational overhead of self-managed build machines that a small team (Document 1 SWOT weakness) cannot easily staff. 12. Monitoring Decision: Cloud Monitoring/Logging (backend) + Crashlytics (mobile crash reporting), as detailed in Document 8 §14. Alternatives considered: Sentry (cross-platform error tracking), Datadog. Rationale: Native GCP/Firebase integration reduces initial ops burden; Sentry remains a reasonable future addition if crash-reporting depth becomes insufficient — flagged as a Document 10 roadmap evaluation item, not a v1.0 blocker. 13.
